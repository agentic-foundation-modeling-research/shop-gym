Problem statement

Whole section

Today ShopGym makes a SandboxShop from one input: a Live storefront, through Storefront exploration and the Shop Manual. Shop generation asks an LLM to invent the whole Dataset: a small catalog, a few Personas with names and addresses, and random seeded orders. Products have no brand, category or attribute fields. No shopper has a history, a taste or a budget. Reviews are random and are not linked to Personas or orders.

This causes these problems for the team:

  1. The catalog is small and not realistic. An agent cannot learn or show search, facet and comparison skills on a few dozen invented products.
  2. The team cannot use the public datasets that it already knows (Amazon Reviews 2023, WebShop, H&M, MerRec, KuaiSearch, OPeRA). Each dataset has its own format. No single ShopGym format exists for a catalog, a user profile or user behavior data.
  3. Personas have no profile and no real history. So ShopGym cannot make personal Tasks ("buy what this user bought next", "reorder my last router") that have one true answer.
  4. The Shop Manual describes pages and features, but it does not record which actions move a shopper from one page type to the next. The Build loop cannot check that every flow of the Live storefront exists in the built shop.
  5. The team wants a first realistic marketplace shop (working name mock_amazon) on Amazon Reviews 2023. No path exists to build it.

Solution

Whole section

Shop generation gets a second input beside the Shop Manual: a Source bundle. A Source bundle is one directory with three optional parts, each in one ShopGym standard schema: a catalog (products and reviews), user profiles, and User events. Thin adapters turn each public dataset into a bundle. Steps then sample the bundle at one cutoff, fill the missing fields (and mark them), and map it to the shop's Dataset plus a hidden users/ directory.

Storefront exploration also writes a Site state graph into the Shop Manual: abstract page states and the actions between them. The Build loop uses it as a list of flows to make and to check. Task generation uses it as a list of flows to expect when it builds its Interaction graph.

Task generation gets a new Generation method, user-first. It reads the hidden user data and makes personal Tasks with a known answer, in the new Task record.

Every shop goes through a Source bundle. A shop with no catalog uses an empty bundle, and the complete step fills it from the Shop Manual (today's LLM catalog synthesis). So old and new shops have one path, one provenance model and one set of checks.

The synthetic data that comes out is for shopping agents: each row is an Accepted task, a reference trace and the Check results.

Terms

These terms go into GLOSSARY.md when the feature ships.

Source bundle
one directory that holds the optional catalog, user profiles and User events for Shop generation, in the ShopGym standard schemas, with one bundle.json that records sources, licenses, locale, currency and cutoff. One bundle can make many SandboxShops.
Avoid: dataset (that is the shop's Dataset), input data.
Adapter
the code that turns one public dataset format into a raw Source bundle. It only renames, regroups and drops fields.
Avoid: converter, loader.
User event
one recorded action of a shopper in a Source bundle, for example a purchase or a search.
Avoid: trajectory (a Trajectory is the record of an agent run), clickstream.
Modeled user
a user in a Source bundle that has one user profile and a time-ordered list of User events. Each modeled user becomes one Persona. Other reviewers are only names on Reviews.
User profile
the structured facts and narrative about one modeled user, in the bundle. It has no account fields.
Avoid: persona (a Persona is the shop account).
Cutoff
the one time per bundle that becomes the start of the Episode clock in the shop. Data before it is shop state. Data after it is hidden.
Task target
a hidden fact after the cutoff, for example the next purchase of a modeled user, that a personal Task asks the agent to reach.
Acceptable set
the set of products, computed by code, that meet every constraint that a personal Task states. The Task passes if the new order holds a product from this set.
Provenance
the per-field mark that says where a value came from: source, inferred, synthetic or rewritten.
sourceinferredsyntheticrewritten
Complete step
the bundle-to-bundle step that fills the fields that a source does not give, and marks them in provenance.
Rewrite step
the optional bundle-to-bundle step that replaces only identifying text and images.
Site state graph
the abstract graph of page states and actions for one storefront. It is part of the Shop Manual and is anonymized like the rest of it.
Avoid: Interaction graph (that is the run-time graph that Task generation builds on one target), transition state, site map.

Implementation decisions

Schema shapes come from the previews approved in the grilling session.

01

One path through a Source bundle

Changed after grilling
  • Every shop goes through a Source bundle. The order is: adapters -> raw bundle -> sample (cutoff, user-first) -> complete (fill + mark) -> optional rewrite -> map to Dataset + users/ -> Build loop.
  • Sample runs before complete, so that the LLM fills only the products that the shop keeps.
  • No catalog input means an empty bundle. For an empty catalog, the complete step synthesizes products from the Shop Manual. This is today's LLM catalog synthesis, moved behind the complete step. All its fields are marked synthetic.
  • The bundle steps run on the core pipeline runner, so --from and resume work as they do for gen today.
  • A bundle is a reusable artifact under outputs/bundles/<name>. One bundle can make many shops.
  • gen --data (task-fe55df99b440) stays a separate, narrow path for now: it copies the Catalog of an existing SandboxShop without change. --data and --bundle cannot be used together. Folding --data into a sandbox_dataset adapter that keeps every id and handle is later work.
02

Source bundle layout

Changed after grilling

Shape from the approved preview, with User events renamed:

<bundle>/
  bundle.json        # name, sources[] (dataset, version, license, url),
                     # locale, currency, cutoff, sample options, seed, created_at
  catalog/
    products.jsonl   # nested products (one line per product)
    reviews.jsonl    # one line per review
    images/          # optional local files
  users/
    profiles.jsonl   # one line per modeled user
  events/
    events.jsonl     # one line per User event

joins (all optional):
  reviews.user_id    -> profiles.user_id
  events.user_id     -> profiles.user_id
  events.product_id  -> products.product_id
  events.variant_id  -> products.variants[].variant_id
  reviews.product_id -> products.product_id
  • Source ids stay as the source gives them (strings). They are unique inside the bundle.
  • One locale and one currency per bundle. English and USD first.
  • Reviews are catalog content. A review's user_id links to a profile only when that reviewer is a modeled user.
03

Catalog standard
  • ShopGym owns the standard. It borrows field names from schema.org Product / ProductGroup and Google Merchant Center where they fit. The goal is the least work per adapter. The Dataset changes only by adding fields.
  • One record is one product with its variants inside.
  • Required at the raw level: product_id, title, at least one variant with a variant_id. Every other field is optional at raw and filled by the complete step.

  • event_type is a closed list: page_view, product_view, search, search_result_click, add_to_cart, remove_from_cart, wishlist_add, checkout_start, purchase, review, return.
  • page_type uses one closed list, shared with the Site state graph and the Interaction graph's Abstract nodes: home, collection, product, search, cart, page, policy, login, register, account, addresses, order detail, checkout, checkout confirmation, other. A new page type is added to that one list, not to one user of it.
  • Orders come from purchase events: grouped by order_id, or by user and session when there is no order_id.
  • AR23 adapter: a verified-purchase review makes a review event plus an inferred purchase event at the review time, with timestamp_precision: order and provenance inferred.   • An adapter drops source event types that do not map to the closed list (for example MerRec offer_make) and counts them in its report.
  • User events are used for seed history, Task targets and graph weights. They are not used as UI-level demonstrations for now.

07

Filling missing user data

All filling is offline, seeded, in the same schemas, and marked in provenance. No LLM shopper browses a hosted shop.

given              -> what the pipeline makes
profiles + events  -> nothing (link check only)
events only        -> profiles: LLM infers them from history (inferred)
profiles only      -> events: sample purchases, reviews, views from the
                      catalog to fit each profile (synthetic, seeded)
neither            -> profiles: LLM writes N (synthetic), then events as above

Every modeled user ends with one profile and a time-ordered list of User events before and after the cutoff.

08

Cutoff, sampling and time shift

Changed after grilling
  • One global cutoff per bundle.
  • Before the cutoff: purchases become orders, and reviews become Reviews, in the Dataset. Ratings are recomputed from visible Reviews. Cart, wishlist and return events stay in the bundle and add graph weights, but they do not become shop state, because the templates have no saved carts, wishlists or returns.
  • After the cutoff: User events are hidden Task targets and are never served.
  • Time shift: the Episode clock always starts at 2026-01-01 (ADR 0009). Shop generation shifts every bundle time by one whole-day offset, so that the cutoff lands on the clock start. The bundle keeps source times. The Shop manifest records the offset. Intents name shifted dates.
  • User-first seeded sampling, size given as bundle options:
    1. pick N users with at least 5 User events before the cutoff and at least 1 purchase after it;
    2. take every product in their histories (before and after the cutoff);
    3. add filler products from the same categories, most-reviewed first, up to the product count;
    4. keep all reviews of kept products (all reviewers); only modeled users get profiles and Personas;
    5. drop products first seen after the cutoff, unless they are Task targets. A target product is listed, and its reviews after the cutoff stay hidden.
09

Complete step and validation
  • The complete step reads a raw bundle and writes a complete bundle in the same schema. It fills gaps by rules first, then by an LLM where rules cannot.
  • Each filled field gets a provenance mark: inferred (derived from other source data) or synthetic (made up).
  • Validation has two levels: raw (the core fields are present and every join resolves) and complete (every field that Shop generation needs is present). Shop generation accepts only a complete bundle.
10

Rewrite step
  • Optional, bundle to bundle, identity only.
  • It changes: titles, descriptions, bullets, brand names (to the fake-brand allowlist, ADR 0013), attributes that name a brand, review text, reviewer names, and images (regenerated).
  • It keeps: all ids, structure, prices, categories, attribute values, ratings and User events.
  • Each changed field gets provenance rewritten.

Mapping to the SandboxShop

Shape from the approved preview:

<shop>/
  shop.json              # + source bundle: name, cutoff, clock offset,
                         #   sources and licenses (next to sourceManuals)
  data/                  # served by the backend
    products.json        # + brand, category, attributes, related, source, provenance
    collections.json     # from category_path
    reviews.json         # Reviews visible before the cutoff (+ customer_id?)
    customers.json       # Personas (accounts), schema unchanged
    orders.json          # Persona orders before the cutoff
  users/                 # never loaded by the backend
    profiles.jsonl
    persona_map.json     # user_id -> customer id
    future_events.jsonl  # User events after the cutoff (Task targets)
  manual/                # incl. site_graph.json
  storefront/  backend/
  • Dataset schema changes are additive only. Shops made without the new fields still load.
  • Dataset ids are numbers. Shop generation assigns them in a fixed order from the source ids, keeps each source id in source, and writes future User events with both the Dataset ids and the handles.
  • Each modeled user becomes one Persona. The customers.json schema does not change. Code makes the email, password and addresses, as Persona synthesis does today.   • The ShopBackend gains read paths for the new fields: brand, category, price and rating facets in search, a rating histogram and review filters on the product page, and related products. Search stays in memory for about 10K products.
  • The SandboxShop's own store name stays a fake name. The working name mock_amazon is only the bundle and output directory name. Product brands may be real when a given catalog has them (see decision 15).

Site state graph

Changed after grilling

Shape from the approved preview, with the shared page types:

manual/site_graph.json
{
  "states": [
    {"id": "search", "page_type": "search", "url_pattern": "/s?k={query}"},
    {"id": "pdp", "page_type": "product", "url_pattern": "/dp/{product_id}"},
    {"id": "cart", "page_type": "cart", "url_pattern": "/cart"}
  ],
  "transitions": [
    {"from": "search", "to": "search", "action": "apply_facet", "params": ["brand"]},
    {"from": "search", "to": "pdp", "action": "open_result"},
    {"from": "pdp", "to": "cart", "action": "add_to_cart", "needs": ["variant"]}
  ],
  "weights": {"source": "user_events"}
}
  • Abstract only: states are page types plus URL patterns, and transitions are action kinds plus params and needs. It has no locators, product ids or real text.
  • Storefront exploration writes it as part of the Shop Manual, anonymized and checked like the rest of the manual. So ADR 0012 still holds.
  • It is not the Interaction graph. The Interaction graph is concrete and run-time: Task generation builds it on one hosted target, with Concrete nodes and checked Edges. The Site state graph is what the Live storefront showed. The Interaction graph is what one shop does.
  • Shop generation adds transition weights from the bundle's User events when they have page types.
  • The Build loop reads it as a list of flows to make. A new Verifier walks each transition on the built shop and fails, naming the transition, when one does not work.
  • Task generation reads it as a list of expected flows. The BFS report lists the transitions that it did not reach.
  • The explore Capabilities schema is extended for marketplace UX: departments, facets, rating histogram, related products.

Personal Tasks: the user-first Generation method

Changed after grilling
  • A new Generation method in Task generation, after BFS + explore. It runs only on a SandboxShop, because it needs users/ and a Persona login.
  • For each modeled user with a Task target, an LLM writes the intent from the user profile and the target's facts (leaf category, key attributes, budget, brand history). The intent does not name the product.
  • Code computes the acceptable set: same leaf category plus every constraint that the intent states.
  • Keep the candidate only if the acceptable set has 5 or fewer products and holds the target.
  • Setup steps log in as the modeled user's Persona through the login form.
  • The reference path comes from the shop's Interaction graph: a checked path from search to checkout, with the target's ids.
  • The candidate then goes through Task generation's acceptance as any other candidate: grounding, the Validation agent, check tests and two fresh replays. Check tests: every acceptable set member passes; a product outside the set, no new order and an old matching order fail.
  • Grading is code-first (ADR 0014). The Backend check is a state_check on the Episode's new order. state_check gets one additive match mode: the resolved array must hold an element that matches any one of a list of candidate values. The Page check on the confirmation page is recorded next to it.
  • Reorder and order-history Tasks use the Persona's orders: reorder is graded by state_check with an exact product and variant; reads use string_match with reference_answers, like the planned account and order reads.
  • Output is the new Task record. metadata.method names user-first and records the user_id, the target event id and the acceptable set. metadata.setup names the Persona.

Example from the approved preview:

target (after cutoff): B09ABC  Acme Mesh Router AX3000
profile: price_sensitivity=mid, household=[partner]

intent: "Our wifi drops upstairs. Get me a mesh router kit that does
         Wi-Fi 6, under $200, from a brand I already own."

acceptable set (code): leaf=Mesh Wi-Fi Systems AND wifi_standard=6
  AND price<=200 AND brand in history brands
  -> {B09ABC, B08DEF}   (size 2, holds target: keep)

Backend check: state_check on the new order's line items:
  some item's product is one of {B09ABC, B08DEF}

Testing decisions

A good test here checks external behavior at the highest seam: given input files, which bundle, shop or Tasks come out. It does not check private helpers, prompt text or the order of internal calls. LLM calls use scripted fakes, so tests are deterministic and offline. Fixtures are tiny (a few products, users and events) and hand-written in the AR23 format, not downloaded.

Four seams. One is new, two exist, and one comes from the Task generation work:

Seam 1

buildBundle (new seam, behind shopgym bundle)

Tests run the AR23 adapter, sample, complete and validate end to end on tiny AR23 fixtures with a scripted LLM. They check:

  • the raw and complete validation levels (a missing core field fails with the record and field name; a broken join fails);
  • user-first sampling (every history product kept, filler from the same category, products first seen after the cutoff dropped unless they are targets);
  • the same options and seed give byte-identical bundles;
  • verified reviews make inferred purchase events; unverified reviews do not;
  • filled fields carry provenance;
  • the empty-catalog case uses the synthesis path and marks every field synthetic;
  • rewrite keeps every id, price, category, attribute value, rating and User event. Prior art: the gen pipeline test (scripted synth LLM plus the fake agent runtime) and the data synth test in ShopArena.
Seam 2

generateShop with a bundle (existing seam)

Tests check that:

  • the written data/ loads through the Dataset loader and the sandbox server serves it;
  • ratings come from visible Reviews only;
  • each modeled user is one Persona with orders before the cutoff, on shifted dates;
  • users/ holds profiles, the persona map and future events;
  • the backend never serves anything from users/;
  • a shop made with an empty bundle still passes the existing gen tests. Prior art: the gen pipeline test.
Seam 3

Task generation run with the user-first method (seam from task-b1d2b014ab34)

Changed after grilling

On a fixture SandboxShop with users/, with scripted LLMs, tests check that:

  • the intent does not name the target;
  • the acceptable set holds the target and has 5 or fewer products, or the candidate is dropped;
  • check tests pass every set member and fail a product outside the set, no order and an old matching order;
  • reorder Tasks have exact answers;
  • output is deterministic for one shop and seed. Prior art: the Task generation fixture shop and check-test design in its spec; the ShopGuru seed test for deterministic generation per seed.
Seam 4

Verifier seam (existing)

Tests check that the new Site state graph Verifier passes when every transition works on a hosted fixture shop, and fails (naming the transition) when one is broken. Prior art: the build Verifier tests.

The core schemas get small table tests only where a rule is not visible through the seams above (for example the closed event_type and page_type lists). The new state_check match mode gets a Grader test beside the existing state_check cases.

Risks and open points

Risks

amazon.com exploration. Amazon's Conditions of Use forbid robots and data extraction tools. Bot blocking can stop exploration. Checkout and account pages stay unseen (the Standard sub-manual covers them, as for every shop). The team chose live exploration with these risks known.

AR23 license. The data has no license and is "primarily for research purposes". Treat every AR23 bundle and shop as research-only and internal. The bundle and the shop record this.

Real brands and names. AR23 brings real brand names and real review text into the shop. The rewrite step is the path to a shop that is safer to share.

Inferred purchases. AR23 has no purchase events. A verified review is only a proxy for a purchase, at the review time. Personal Task targets have this noise.

No variant options in AR23. Metadata is per parent product, with no option table and no per-variant price. The complete step infers options and marks them.

Scale. About 10K products and 50K images (a few GB) per shop. Search is a linear scan in memory.

Dependencies. The user-first method needs the Task generation pipeline and the new Task record (task-b1d2b014ab34). The Reviews, Personas and --data work (pr/44, pr/45, pr/53, pr/54) must land first, because this spec extends their schemas.
