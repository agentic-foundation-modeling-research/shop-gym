ShopGym design review · 2026-10-29

Task generation: BFS + explore

A plan to make shopping Tasks that are proven solvable and graded by code. The same method runs on a SandboxShop and on a real Shopify shop, so that we can compare an agent's results on both.

spec: ready-for-agent parent: task-b1d2b014ab34 21 tickets new package: @shop-gym/task-generation ShopGuru: deprecated
Summary

In one minute

What we build

A new package and command: shopgym tasks --config <path> [--from <step>]. It runs four Steps: explore, expand, compose, validate. ShopGuru keeps working, but it gets no new features.

How it works

An LLM Explorer agent proposes. Code replays and accepts. BFS grows the Interaction graph and tries what the agent skipped. An LLM writes the intent. Code writes the Checks from the state diff.

Why we can trust a Task

A Task is Accepted only after 4 gates: grounding, a Validation agent run from the intent alone, check tests, and 2 fresh replays. No LLM judge grades any Task.

First trial

mock_clothing_v2 plus 1 apparel Live storefront. Target: 30 Accepted tasks per shop. The report gives yield, cost and how often Page checks disagree with Backend checks.

What we ask the team to review

  1. Graph rules. Are "2 of 2 fresh replays", "flaky after 2 failures" and "split only when outcomes repeat" the right strictness? (1.2)
  2. Task record. Does WebArena's format plus state_check and metadata work for our RL environment? How should a Check say "exactly these lines, in any order"? (2, 4)
  3. Trial bar. Is 30 per shop, with at least 3 per intent class, the right bar? Which Live storefront do we use? (3)
  4. Models. Is it OK that claude-opus-5-5 both writes intents and validates them, and so can never be an evaluated model? (4)
  5. Cost. What cost per Accepted task makes BFS + explore worth keeping? We suggest that we agree on a limit before the trial. (4)
Focus 1 · Algorithm

1. How it works: four Steps

Each Step writes files. --from <step> runs one Step again, and every Step after it, without the work before it. This is the same pattern as shopgym explore and shopgym gen.

Who decides: the LLMs propose, code decides

Four roles use an LLM. Every decision that lets something into the graph or into the benchmark is made by code, or by the Validation agent's real run in the browser.

All four models are configurable. Each Task records the models that made it. The Validation agent must never be a model that we evaluate.

Focus 1 · Verification

    
1.2 How we verify the graph and the Tasks

    
Two levels of proof. First, each Edge must reproduce. Then, each candidate Task must pass four gates.

  


  
Edge life cycle

  

  

    

      nodes
      
Two levels of node

      
Abstract node = page type from the URL pattern, plus 2 flags: cart empty or not, signed in or not. BFS uses it, so the graph stays small.

      
Concrete node = the Abstract node plus the exact /cart.js lines, the product shown, the selected variant, the quantity input value and allowlisted query parameters. In a SandboxShop it also holds an account signature from the StateSnapshot. Replay uses it, so a replay is exact.

    

    

      self-loops
      
Quantity is a tagged self-loop

      
"+" on the cart page does not change the Abstract node. So it is a self-loop, tagged with its cart-line diff ("Joggers M: 1 → 2"). Quantity workflows become Tasks, and there is no node per quantity. A cap limits self-loops per path.

    

    

      splitting
      
Split only when outcomes repeat

      
A node splits only when one control gives different outcomes on pages of the same Abstract node, and each outcome repeats at its own Concrete node. The split feature comes from a fixed list: has variants, sold out, has a quantity input. If the outcomes do not repeat, the Edge is flaky.

    

    

      controls
      
Do not spend budget on copies

      
Code removes duplicate controls by role, masked name (digits and prices hidden) and page region. Listing pages sample 1 to 3 product cards by their features. A control counts as tried only after its outcome is recorded.

    

  


  
Budgets per shop

  

    
6depth, in semantic transitions

    
50Abstract nodes

    
4,000primitive browser actions, prefix replays included

    
capscontrols per node, Concrete nodes per Abstract node, self-loops per path

  

  
We calibrate the budgets on the development SandboxShop, then freeze them. The untested frontier is kept and reported. The graph is cached by storefront, backend and Dataset versions (sandbox), or by URL, capture time, locale and evidence fingerprints (live).


  
Acceptance: four gates after compose

  

    

      
GateWhat it checksIf it fails

      
        
0. Dedupe (in compose)One candidate per workflow-goal signature: intent class, constraint structure and required state changes, without product ids or wording.dropped as duplicate

        
1. GroundingEvery value in the Checks comes from the intent, the start state or a fact that was visible on a page of the path. In a SandboxShop, a selection rule ("highest-rated") must have exactly one answer in the Dataset. A tie rejects.task defect

        
2. Validation agentpi with the standard browser tools, pinned to one model. The runner replays the Setup steps in a Fresh context and confirms the start signature. The agent gets only the intent and the start URL, and must end at finish with the Checks passing.environment failure if the start signature does not match. Otherwise unresolved, with a class: task defect or validator failure

        
3. Check testsNo browser. Valid alternatives must pass (other action orders from the graph). Targeted violations must fail: unchanged start, wrong quantity, wrong variant, missing kept line, extra line, old matching order, no code, wrong code, code that does not apply, wrong address, wrong default address, recovery request for another email.task defect (the Check is wrong)

        
4. Two fresh replaysThe reference path, replayed twice in Fresh contexts, must pass the Checks both times.environment failure

      
    

  

  
After the gates, difficulty comes from the efficient replay's count of primitive browser actions: Easy ≤ 3, Medium 4 to 9, Hard ≥ 10. Structure tags add constraint count, cross-page evidence and planning. Shortages are reported. We never relax a gate to reach 30.

Focus 4 · Also important

    
4. Open questions and risks

    
Items that the spec leaves open, or that we found while we made the examples on this page. Items marked "suggestion" are not in the spec.

  

  

    

      
decide in ticket 9found while writing this page

      
How does a Check say "exactly these lines, in any order"?

      
Today's matchers cannot say it alone. equals compares arrays in order and counts every key, so a cart line's id breaks it. subset allows extra lines. Old orders are in the StateSnapshot too, so a checkout Check must look only at new orders.

      
Suggestion: the Task generation grader applies metadata.equivalence before it matches: drop ignored paths, compare listed arrays as multisets, and keep only orders whose ids are not in the start signature. The examples on this page use this shape (ignore, unordered, orders: new_since_start).

    

    

      
decide before the trial

      
One model writes the intent and also validates it

      
The intent writer and the Validation agent are both claude-opus-5-5. They can share blind spots: an intent that only this model reads one way can still pass. Also, claude-opus-5-5 can never be an evaluated model. Today's solver audit set (gpt-5.6-luna, claude-sonnet-5-5, claude-haiku-5-5) does not include it, so the rule holds for now.

      
Suggestion: keep the defaults for the trial, but report the result if the Validation agent is a different model family on a sample of candidates.

    

    

      
watch in the trial

      
The explorer's model is also an evaluated model

      
The Explorer agent and the Action chooser use claude-sonnet-5-5, which is in the audit set. Code checks every Edge, but what the explorer finds shapes the Task mix. This can favor workflows that this model finds easy.

      
Suggestion: look for this bias in the per-model results. BFS tries the skipped controls, which reduces it.

    

    

      
decide before the trial

      
Cost is unknown until we calibrate

      
Each candidate Edge costs 2 replays of its prefix. Each candidate Task costs a Validation agent run on claude-opus-5-5. The budget is 4,000 primitive actions per shop, but the model cost per Accepted task is not known yet.

      
Suggestion: agree on a cost limit per Accepted task now, so that the keep-or-stop decision after the trial is objective.

    

    

      
decide before the trial

      
Which Live storefront?

      
Required by the spec: apparel, a Shopify online store that serves /cart.js, guest carts, and it passes the robots.txt, rate-limit, user-agent and bot-challenge gates. Helpful: size variants, a quantity input, collections and search, some sold-out variants, one currency.

      
Suggestion: also read the shop's terms of service for automated browsing before we pick it.

    

    

      
known limit

      
Live Page checks have no ground truth

      
On a Live storefront the Page check decides, and nothing checks it. The sandbox disagreement rate between Page checks and Backend checks is our only estimate of its error. Live Tasks are invalidated when prices, stock or controls change.

    

    

      
dependency

      
Commerce classes wait on sibling work

      
Five intent classes need task-50bc4d23931e: Discount codes, Reviews, Personas with orders, the address book, login and password recovery. The pipeline, the shared browser and Harness changes, and the cart Tasks do not. If mock_clothing_v2 is generated before ticket 2, we must generate it again.

    

    

      
confirm in ticket 2

      
/cart.js parity with Shopify

      
The template route must use Shopify's AJAX cart field names, so that one Page check works on both kinds of shop. The exact field set must be confirmed against Shopify's documentation.

    

    

      
suggestion

      
No human reads an Accepted task

      
Every gate is automatic. A Task can pass all four gates and still have an intent that is clumsy, or that gives away the clicks.

      
Suggestion: two team members read a sample of about 10 Accepted tasks per shop in the trial, and we report what they find.

4.2 Prior art: what we take, and what we avoid

    
We read the code of four MIT projects. Their code is Python, so reuse means a TypeScript rewrite that keeps the license notice.

  

  

    

      
SourceWe takeWe avoid

      
        
AutoWebWorld
arXiv 2602.14296, MIT		BFS over states. A path to a goal becomes a task. Replay validates it.Its state machine is written by hand for synthetic sites. We infer ours from a real UI.

        
DroidBot
github repo, MIT		State hashing with a content-free variant. Shortest path in the UI graph. A missed-states list.The random-mode fallback after restarts.

        
SynWeaver
arXiv 2608.12429, MIT		Shortest-path replay with a check after each step. Programmatic checks.Marking a control tried before it acts. Checking only the end state after a replay.

Focus 4 · Also important

    
4.3 Test seam, scope and terms

  

  

    

      
One test seam

      
Tests drive the pipeline function only. FakeRuntime scripts the Explorer agent, the Action chooser and the Validation agent against the real browser tools. A fake LlmClient plays the intent writer. Real Chromium runs against a small node:http fixture shop. In sandbox mode the fixture calls the real ShopBackend in process. In live mode it keeps a guest cart in memory. So one fixture acts as both kinds of shop.

      
A live test behind SHOPGYM_LIVE=1 runs one short real-model exploration and one validation.

    

    

      
Out of scope for this spec

      
    
        
  • The template and product-first Generation methods, and the keep/drop gate that needs them
    • 
        
  • The full pilot: 6 SandboxShops, 3 Live storefronts, 900 Tasks
    • 
        
  • RL training and the before/after RL evaluation
    • 
        
  • New commerce features (returns, cancellations, saved payments, wishlists). Writing Reviews. Completing a password reset.
    • 
        
  • Login, checkout, Discount code, Review and account Tasks on Live storefronts
    • 
        
  • LLM-judge-graded Tasks and subjective recommendations
    • 
        
  • Event-order Checks (the backend has no event log)
    • 
        
  • Removing ShopGuru, or converting its Tasks
    • 
        
  • An evaluation runner or environment server, beyond the Validation agent
    • 
      

    

  

  
Terms

  

    
Task generation
The new package and Step pipeline that makes Accepted tasks for one shop.

    
Generation method
One way to make candidate Tasks. BFS + explore is the first.

    
Intent / Intent class
The shopper's goal in words. The class groups intents by workflow, such as cart edits.

    
Interaction graph
The shop's checked UI behavior: nodes are states, Edges are single UI actions.

    
Abstract node
Page type plus the cart-empty and signed-in flags, plus proven split features.

    
Concrete node
An Abstract node plus exact cart lines, product, variant, quantity input and query parameters; in a sandbox, also the account signature.

    
Edge
One UI action with a stable locator, its cart (and account) diff and every recorded outcome.

    
Fresh context
A new episode id (sandbox) or a new guest browser context (live). The only way to a clean state.

    
Setup steps
Recorded UI steps that reach a Task's start Concrete node, plus its expected start signature.

    
Explorer agent
The Harness run that browses area by area and proposes candidate Edges.

    
Action chooser
The LLM that picks untried controls, and text values, at a BFS node.

    
Validation agent
pi, pinned to one model that we never evaluate. It must solve the Task from the intent alone.

    
Backend check / Page check
A Check on the StateSnapshot, or a Check on a page such as /cart.js.

    
Accepted task
A candidate that passed grounding, the Validation agent, check tests and 2 fresh replays.
